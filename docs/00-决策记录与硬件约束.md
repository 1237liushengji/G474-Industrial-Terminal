## 1. 硬件事实与不可逾越的约束

### 1.1 拥有的硬件

| 资产 | 数量 | 说明 |
|---|---|---|
| DRG ST-10 STM32G474VET6 开发板 | 2 | 板载 RS485、CAN 位（PB12/PB13）、WiFi 位（PB10/PB11）、板载 USB 转串口 |
| 1.69″ SPI TFT（ST7789, 240×280） | 2 | 软 SPI 驱动已在 Modbus 工程 v2.0 调通 |
| ESP-12F（ESP8266EX，2.4 GHz only） | ≥1（已确认有多余一片） | 挂在板上 WiFi 排针，与 RS485 共用跳线帽 |
| 板载 24C02（I2C1）、W25Q128（SPI1）、按键 WKUP/K0/K1 | 每板各一组 | |
| USB-RS485 转换器 | **0** | 未持有 —— 直接决定形态 M1/M2 的分界 |
| USB-CAN 适配器 | **0** | 未持有 —— CAN 段验收只能靠板端 stats + 串口日志交叉 |

### 1.2 引脚级互斥（本方案最关键的物理约束）

STM32G474 的 AF 映射表（RM0440 / 数据手册 Table 13）中：

- **PB10 只有一个 USART 复用：USART3_TX(AF7)**
- **PB11 只有一个 USART 复用：USART3_RX(AF7)**

本项目的两份既有文档已各自记录过同一事实：
- `Modbus-RTU/docs/02-板级硬件配置.md:10-11` —— RS485 用 PB10/PB11，"WiFi 复用 PB10/PB11，与 RS485 共用同一 USART3，本项目不使用"
- `Modbus-RTU/docs/02-板级硬件配置.md:37` —— "PB10 仅可作 USART3_TX(AF7)，PB11 仅可作 USART3_RX(AF7)"

**推论（不可绕过）**：在单块板上，板载 RS485 与 WiFi 排针**严格二选一**。跳线帽共用不是布线失误，而是芯片复用矩阵决定的。
不做飞线/割线的前提下，**"同一块板同时拥有 RS485 和 USART3-WiFi" 不存在任何软件解法**。

### 1.3 可用的独立通道（已实测验证）

| 通道 | 引脚 | 证据 |
|---|---|---|
| USART1（板载 USB 转串口 → PC COM 口） | PA9=TX / PA10=RX | CAN 工程 v3.0 用其跑 console + `tools/can_console.py` 实测通过；厂商 `2.参考例程/3.USART` 同用 USART1 + `GPIO_PIN_9\|GPIO_PIN_10`（`Core/Src/usart.c:102`） |
| FDCAN2 | PB12=FDCAN2_RX / PB13=FDCAN2_TX，AF9 | CAN 工程 v3.0 双机实机通；README §3 位时序核算 |
| SPI1（W25Q128） | PA4=CS / PA5=SCK / PA6=MISO / PA7=MOSI | Modbus 工程 v1.1 |
| I2C1（24C02） | PA15=SCL / PB9=SDA | Modbus 工程 v0.9（**尚未真机验证**，见 §1.4） |
| LCD 软 SPI | PD11=CS / PB3=SCL / PB5=SDA / PD12=DC / PD13=BL | Modbus 工程 v1.0 + v2.0 后修复链 |
| 按键 | PA0=WKUP / PA2=K0 / PA3=K1 | Modbus 工程 v1.0 |
| LED | PE0=蓝 / PE1=绿，低电平点亮 | 两工程一致 |

**USART1 与 FDCAN2 可同时在用**（CAN 工程 v3.0 即为此配置），这是本方案能保住 console/上代理链路的依据。

### 1.4 必须注意的调试器与引脚残留风险

- **PA15（24C02 SCL）与 PB3（LCD SCL）在复位后默认属于 SWJ 引脚（PA15=JTDI，PB3=JTDO/TRACESWO）。**
  调试必须锁定 **SWD 2-pin 模式（仅 PA13/PA14）**，禁止启用 JTAG 或 Trace，否则 I2C1 与 LCD 同时失效。
  Modbus 工程 README 的验收矩阵把 24C02 一栏标为"待真机"，此风险很可能就是原因之一。
- W25Q 型号在不同文档间不一致：Modbus 工程按 **W25Q128 / 16 MB** 实现，厂商例程目录名为 **5.W25Q64**。
  上电必须读 `W25Q_ReadID()` 并核对 JEDEC ID，**不得假设容量**；`LOG_AREA_BASE = CAPACITY - 64KB` 依赖该常量。
- CAN 工程未提交改动：`G474.uvprojx/.uvoptx` dirty。Modbus 工程未提交改动：`BSP/bsp_board_cfg.h`
  的 `MODBUS_NODE_ROLE` 被从 SLAVE 翻成 MASTER。**合并前必须各自 commit 或 stash，避免把脏状态带入新仓。**

## 2. 决策记录

### D-01 演进优于重写：以两个既有工程为唯一基线

**决策**：新系统不写新驱动、不写新协议栈。CAN 工程出 FDCAN/ISO-TP/UDS/console，Modbus 工程出 RS485/Modbus/BSP/Storage/Tools，
两边协议层几乎原样搬入，只在 `Gateway/` 与 `Network/` 写新代码。

**理由**：Modbus 工程已到 v2.0（15 个 tag、30 commit、11 条黄金测试向量、Node 交叉验证 256/256 CRC 表项），
CAN 工程 v3.0 已解决 FDCAN 上三个真实 HAL 陷阱。重写等于丢弃这些已付成本。

### D-02 RS485/Modbus 段与 WiFi 段的物理归属 —— ⚠ **已作废，见 07 §4 C2/C3**

**原决策**：以"谁占用 USART3(PB10/PB11)"作为两形态的唯一分水岭，其余架构完全共用。见 §3。
**作废理由**：PB10/PB11 的复用唯一性成立，但 RS485 与 ESP-12F 都是外接模块，且 USART3/USART2 另有
空闲引脚对可用 → 无需二选一。**取代决策**：RS485 → USART2 on PD5/PD6；ESP-12F → USART3 on PB10/PB11。

**理由**：受 D-01 与 §1.2 约束，任何形态下每块板的 USART3 只能给一个功能。因此"RS485 段在系统内闭环"
与"MQTT 协议栈跑在 MCU 上"这两个目标，在**只有两块板、没有 USB-RS485** 的条件下不能同时达成。
用两种形态覆盖，而不是伪造成一种能同时满足的方案。

### D-03 B 板做 Modbus 从站，主站角色外部化

**决策**：B 板沿用已验证的 `Slave/slave_main.c`（TFT 三页 UI + 24C02 参数保存 + 环形日志）做从站，
Modbus 主站由 PC 侧（`Tools/python/modbus_master.py` + `modbus_tool.py`）或外部 USB-RS485 承担。

**理由**：`slave_main.c` 460 行、含完整 UI/配置/日志路径，是三份应用代码里成熟度最高的一份；
`master_main.c` 无 UI、测量量为硬编码。让 B 板做从站可做到固件近零改动。

### D-04 MQTT 协议栈位于设备侧（A 板），ESP-12F 降级为 TCP 管道

**决策**：A 板移植 **MQTT-C**（`LiamBindle/MQTT-C`，单 `mqtt.h/mqtt.c`，无 OS 依赖），
ESP-12F 只跑 AT 建立 TCP 连接并进入透传模式，不承担 MQTT 语义。

**理由**：
1. 不赌出厂 AT 固件版本 —— ESP-AT 1.7.x 无 `AT+MQTTUSERCFG` 系列指令，需先用 USB-TTL 刷 v2.x；本决策消除该依赖。
2. QoS1 重发、keepalive、离线补发的状态机必须与 W25Q128 缓存同处一个 MCU 才可核算（见 D-06）。
3. MQTT-C 报文序列化/解析可与 Modbus 协议层一样保持"HAL-free + 时间由调用者注入"，从而复用 PC 侧离线测试能力。

**代价**：透传模式下 AT 指令不可用（需 `+++` 逃逸），必须设计 AT 窗口仲裁状态机 —— 记入 §5 风险 R-3。

### D-05 引入 FreeRTOS，且这是 v0.2 的主要工作量

**决策**：合并后的固件采用 FreeRTOS（用户选定）。协议层不做 RTOS 改造，改造集中在 BSP 与新增任务。

**理由**：目标系统同时存在 RS485 逐字节时序、CAN 收发、ESP-12F AT 状态机、LCD 重绘（全屏清约 100 ms 量级）、
flash 阻塞写 —— 裸机协作循环要同时不饿死这些任务，分时预算会非常紧张。

**必须一并完成的三件事（缺一即整体不可用）**：
1. **HAL 时基迁移**：FreeRTOS 接管 SysTick 后 `HAL_GetTick()`/`HAL_Delay()` 停滞。
   须重定向 `HAL_InitTick()` 到 TIM6 1 ms（Modbus 工程 docs/04 §2.3 曾"计划"用 TIM6 但代码里未实现）。
2. **中断优先级整改**：设 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`。
   现有 FDCAN2 优先级 (1,0) **数值高于（抢占强于）5，在其中调用 `xQueueSendFromISR` 属非法**，
   须把 FDCAN2 降到 (6,0)、USART3 由 (5,0) 调整为 (6,0)，并全表登记（见 04 号文档 §5）。
3. **阻塞点出主路径**：`RS485_SendFrame()` 内的 `while(!(ISR&TC))` 忙等、`LOG_WriteEvent()` 的阻塞页编程、
   `CONFIG_Save()` 的 I2C ACK 轮询（50 ms 超时）必须改为队列 + 专用任务，否则违反"上云不得阻塞轮询"的约束。

### D-06 唯一数据契约 = B 板保持寄存器表；三协议均为其投影

**决策**：不引入独立的"数据点数据库"。`Protocol/modbus_register.h` 的保持寄存器表就是全系统唯一契约，
CAN 帧是它的投影，MQTT payload 是它的另一层投影。契约版本号写死为常量并随 `meta` 主题上报。

**理由**：Modbus 侧已有 15 个保持寄存器、读写权限谓词、量程校验、24C02 持久化字段、Python 仿真器与黄金向量。
再建一层数据模型必然产生两份真相。详见 03 号文档。

**约束**：既有地址 0x00–0x0E 的语义、量程、默认值、持久化字段**一律不改**（否则 `modbus_slave_sim.py` 的
`DEFAULT_HOLDING`、`format_holding_value` 与 24C02 记录同时失效）。新数据点从 **0x10** 起分配，
0x0F 与 0x18–0x1F 保留为协议/契约元数据。

### D-07 离线缓存放设备侧，复用 W25Q128 环形日志的机制而非另写一套

**决策**：MQTT 未确认发布的报文，序列化后作为一条新事件类型写入 `Storage/log` 的既有环形区，
恢复后按 `seq` 顺序补发。不新增第二套 flash 分区管理。

**理由**：`Storage/log.c` 已实现扇区轮转 + 上电线性扫描恢复 + `seq` 连续性判定 + RAM 缓存，且 `seq` 天然就是补发顺序键。
复用可省掉一整套磨损均衡/掉电一致性代码，代价是要处理"同一块区域既存事件日志又存待发报文"的容量分配（见 R-5）。

### D-08 双板角色用单一配置点，且必须升级为 Keil 双 Target

**决策**：`App/app_board_cfg.h` 为唯一可变点，派生节点角色、USART3 归属、MQTT 参数、轮询周期。
角色选择在 MDK 里建成两个 Target（`G474_A_GW` / `G474_B_NODE`），通过 Define 字段注入，
不再靠手改头文件。

**理由**：两个既有工程各有一个名叫 `G474` 的 Target，且 Modbus 的角色宏 `MODBUS_NODE_ROLE` **不在** Define 字段里
（只改头文件切换），导致 `master_main.c`/`slave_main.c` 永远一起编译链接 —— 与自身文档 docs/01 §3 矛盾，
且极易烧错固件。烧错一块板在双机系统里表现为"链路不通"，排查成本极高。

### D-09 broker 部署在 PC 本机

**决策**：Mosquitto 2.1.2，安装于 `E:\Edge\mosquitto-2.1.2`。
ESP-12F 与 PC 同处一个 2.4 GHz LAN；`mosquitto.conf` 需 `listener 1883 0.0.0.0` + `allow_anonymous true`（实验网），
并放通 Windows 防火墙入站 1883。

**理由**：PC 上当前无 docker、无 mosquitto 服务、Python 3.14 仅有 pyserial；用户已自行安装 Mosquitto。
本机 broker 可让"断 broker"成为可控故障注入项，且不依赖外网。

## 3. 两种闭环形态 —— ⚠ **整节已作废，见 07 号文档 §5**

> 本节成立的前提是"单块板不能同时拥有 RS485 与 WiFi"。07 号文档 §2/§4 证明 RS485 与 ESP-12F
> 都是**外接模块、走排针接线**，改线即可并存 → 前提消失。**请直接阅读 07 号文档 §5 的修正拓扑**：
> 两板同构，均具备 RS485(USART2/PD5,PD6) + ESP-12F(USART3/PB10,PB11) + CAN(FDCAN1/PD0,PD1) +
> 板载 16MB Flash(SPI2/PB12-PB15)，A 板做 Modbus 主站 + 上云、B 板做从站 + 本地 HMI。
> 下文仅作历史记录保留，**不要按此实施**。

### M1 · 零采购形态（当前配件即通，作为 v0.x 开发基线）

```
PC: USB-RS485? 不需要
    ├── COM口 ← USART1(PA9/PA10) ← A板 板载USB转串口
    └── Python 影子网关 → publish → Mosquitto(本机:1883)

A板(GATEWAY): USART3 = 板载RS485 = Modbus 主站
              FDCAN2 = CAN 节点
              USART1 = console + 上行走自定义帧 → PC
              TFT = 监控页
              W25Q128 = 事件日志 + 待发缓存
B板(NODE):    USART3 = 板载RS485 = Modbus 从站（固件近零改动）
              FDCAN2 = CAN 节点，周期上报寄存器快照
              TFT = 数据页 + 按键改参数
              24C02 = 参数持久化
```
- 四链路中 **RS485、Modbus、CAN 三条真实在线**，MQTT 在 PC 侧。
- 优点：立即可跑、可回归、Tools/python 全套复用、零风险。
- 缺点：MQTT 不在设备上，与产品形态偏离 —— 因此它只作为阶段三的**第一个可验证里程碑**，不是终点。

### M2 · 目标形态（差一只 USB-RS485 或 TTL↔RS485 小板）

```
PC: USB-RS485 ──RS485总线(A/B)──┐          Mosquitto :1883
    Modbus 主站(仿真现场PLC/仪表) │               ▲
                                  ▼               │ Wi-Fi (2.4G)
                            B板(NODE)        A板(GATEWAY)
                            USART3=RS485从站 ←─CAN─→ USART3=ESP-12F #1
                            TFT/24C02/日志            MQTT-C + W25Q128 缓存 + TFT 监控页
                                                      USART1 = console
```
- **RS485 + CAN + Modbus + MQTT 四链路同时在线，MQTT 在 MCU 上**。
- A 板永久让出 RS485（§1.2），RS485 段整体下移到 B 板。
- 关键验收红利：同一条测量量经**两条独立路径**到达 PC —— PC 用 Modbus 主站直读 B 板寄存器，
  同时从 mosquitto 收到 A 板经 CAN 转发后的同值。两路可比对，是系统级自证手段（见 05 号文档 A-06）。
- ESP-12F #2：作为可选的 B 板第二上云通道（B 板若让出 RS485 则同 M2-A 对称），默认**不使用**，
  留作 M1↔M2 切换时的备件与第二形态试验件。

### 形态切换成本

| 项 | M1 | M2 | 切换动作 |
|---|---|---|---|
| `BOARD_UP3_OWNER` | `UP3_RS485` | `UP3_ESP` | 改 1 个宏 + 换跳线帽 |
| MQTT 实现 | PC `paho-mqtt` | A 板 MQTT-C | 换 `Gateway/` 编译单元（同一 `uplink_port` 接口） |
| Modbus 主站 | A 板 `MB_Master_*` | PC `modbus_master.py` | 固件 Target 切换 |
| 其余（契约/CAN/主题/任务表/UI/Storage） | 完全相同 | 完全相同 | 无 |

## 4. 范围裁剪（明确不做）

- 经典 CAN 500 kbit/s 为唯一 CAN 配置；**不做 CAN FD**（硬件是 FDCAN 且驱动支持，但既有位时序表按经典帧核算，切 FD 等于重算并推翻 v3.0 已验证结论）。
- Modbus **只做 RTU**；TCP 仅在 `Protocol/modbus_port.h` 预留传输抽象位，不实现。
- 不引入未持有硬件（USB-RS485 缺口用 M1 绕过，而非偷偷假设其存在）。
- 不做 UDS/ISO-TP 诊断的产品化扩展：ISO-TP **仅**被复用为 CAN 上的全表快照载体，UDS 保留但不在验收路径上。
- 不补 RTC 时间戳（`log_record_t.timestamp_ms` 仍为 uptime，跨重启不可比 —— 记为已知限制 L-2）。

## 5. 风险登记

| ID | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R-1 | PA15/PB3 属 SWJ 引脚，误开 JTAG/Trace | 24C02 + LCD 同时失效，表现为"从站不响应 + 白屏" | 锁定 SWD 2-pin；v0.1 就做一次 24C02 真机读写验收 |
| R-2 | FreeRTOS 接管 SysTick 后 HAL 时基停滞 | 所有 HAL 超时立即返回，FDCAN/UART 状态机疯转 | `HAL_InitTick` 重映射 TIM6；验收项 A-02 专项 |
| R-3 | ESP-12F 透传模式下 AT 不可用 | 断线后无法重连，卡在透传 | AT 窗口仲裁状态机：`+++` 无守卫时间 + 独立 `at_window` 标志 + 超时兜底 |
| R-4' | ESP-12F 峰值电流 300–400 mA；板上 LDO 为 **AMS1117**（线性，5V→3.3V 每 100 mA 耗散 0.17 W），且 3.3V 轨**仅 10 µF 储能** | 发射瞬间压降/复位，表现为随机重启 | 给 ESP-12F 就近并 220–470 µF 电解 + 10 µF 陶瓷；必要时为模块单独供电。详见 07 §8 V-3 |
