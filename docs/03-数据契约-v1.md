# 03 · 数据契约 v1（寄存器 ↔ CAN ↔ MQTT 三方映射）

> ⚠ **本文件受 [07 号文档](07-板级硬件核对与冲突修正.md) 修订（2026-09-21）**：
> - §4.1/§4.2 的 CAN **控制器实例由 FDCAN2 改为 FDCAN1**（引脚 PD0/PD1）；**位时序与全部帧 ID 分配不变**。
> - §4.4/§5.3 的容量核算：板载 W25Q128 确认可用后，`LOG_AREA_SIZE` 由 64 KB 提升到 **256 KB**，
>   32 B 记录容量 2048 → **8192 条**，断网缓冲由 ≈26 min 提升到 **≈105 min**（按 50/50 配额约 52 min）。
> - 其余（寄存器总表、CAN 帧内字节布局、过滤器、MQTT 主题/payload、契约哈希）**全部保持有效**。

> 本文是全系统**唯一**的数据真相源（依据 00 号文档 D-06）。
> 任何一侧新增/改动数据点，必须先改本表，再改代码，最后重算契约哈希。
> 冻结基线：`CONTRACT_VERSION = 1`。

## 1. 三方映射的层次关系

```
              ┌──────────────────────────────────────────┐
              │  契约层：dp_table[]（本文件 §3，编译期常量）│
              └──────────────────────────────────────────┘
                      ▲              ▲              ▲
             投影 1   │     投影 2   │     投影 3   │
   ┌──────────────────┴─┐  ┌─────────┴────────┐  ┌──┴───────────────────┐
   │ Modbus 保持寄存器   │  │ CAN 帧（投影）    │  │ MQTT 主题/payload     │
   │ B 板持有，0x03/06/10 │  │ B→A 周期搬运      │  │ A 板序列化发布         │
   └────────────────────┘  └──────────────────┘  └───────────────────────┘
```

- **存储只有一份**：B 板 `Protocol/modbus_register.c` 的 `s_holding[]`。CAN 不引入第二套数值语义，
  MQTT 不引入第三套。
- **投影是纯函数**：`dp_table[]` 一张编译期常量表同时驱动 Modbus 地址解析、CAN 打包、MQTT 序列化，
  避免三处手写 while 只改一处。
- **一致性自动校验**：契约哈希 `contract_hash = MODBUS_CRC16(dp_table 描述串)`，
  写入寄存器 `0x18`（RO，可被 PC 用 0x03 直读）、写入 `meta` 主题、写入 CAN 快照头部。
  三者任一不等即判定固件与本表不同步。

## 2. 命名与地址空间约定

| 项 | 约定 |
|---|---|
| Modbus 显示地址 | `40001 + PDU地址`（`40001` ↔ PDU `0x00`） |
| PDU 地址空间 | 16-bit，本项目仅用 `0x00–0x3F` |
| 数据点键名 (`key`) | 小写下划线，全局唯一，同时作 MQTT JSON 字段名 |
| 刻度 (`scale`) | 定点小数位数（0/1/2），物理值 = raw / 10^scale |
| CAN | 11-bit 标准帧，经典 CAN，500 kbit/s，采样点 80% |
| MQTT | 前缀 `gac/{site}/{gw}/`，`site=line1`，`gw=gwA`，节点后缀 `n0`(A板) / `n1`(B板) |
| 字节序 | **Modbus 与 CAN 多字节一律 BE**（与既有 `MB_REG`/`CAN_EncodeCmd` 风格一致）；CRC 按 Modbus 规定 **LE 在前** |

### 2.1 兼容性红线（不可违反）

既有 Modbus 工程 v2.0 已冻结的内容**一律不改**，否则 `modbus_slave_sim.py::DEFAULT_HOLDING`、
`modbus_tool.py::format_holding_value`、11 条黄金向量、24C02 的 17 字节记录 同时失效：

1. `0x00–0x0E` 全部 15 个保持寄存器的语义、量程、只读/可写属性、上电默认值 —— 原样保留（下表标 `[v1保留]`）。
2. 可写谓词仍为 `addr ∈ [0x09, 0x0E]`；`0x0F` 必须继续返回异常 `0x02`（越界），即使 `MB_REG_HOLD_COUNT` 已增大。
3. 24C02 持久化字段集合仍恰好是 `0x09–0x0E` 这 6 个（`config_record_t` 为定长 17 字节，加字段需 `CONFIG_VERSION=2` 迁移，排到 v1.x）。
4. 波特率索引表为 5 项 `{9600,19200,38400,57600,115200}`，`MB_BAUD_IDX_MAX=4`。
   `docs/03` 与 `modbus_tool.py` 里残留的"6 项含 230400"是**过期文档**，以代码为准（收发器未达额定速率，v2.0 已删除 230400）。
5. `0x04`(读输入寄存器) / `0x05`(写单线圈) 在 v2.0 固件里 **无 handler，返回异常 0x01**。本契约选择"实现 0x04"而非删除契约，见 §4.3。

## 3. 数据点总表 `dp_table[]`

### 3.1 区段划分

| PDU 区间 | 用途 | R/W | 持久化 | 状态 |
|---|---|---|---|---|
| `0x00–0x08` | 实时测量 + 设备状态 + 通信计数 | RO | — | `[v1保留]` 0x00–0x0E 段内 |
| `0x09–0x0E` | 现场可编辑配置 | RW | ✅ 24C02 | `[v1保留]` |
| `0x0F` | 空洞，越界保护哨兵 | — | — | 写→0x02 |
| `0x10–0x17` | 网关侧与 CAN 骨干统计 | RO | — | **新增** |
| `0x18–0x1F` | 契约元数据（版本/哈希/形态/心跳） | RO | — | **新增** |
| `0x20–0x2F` | 扩展测量量（真实传感器/ADC 上收） | RO | — | **新增** |
| `0x30–0x3F` | 下行命令影子寄存器（MQTT→CAN→Modbus） | RW | ❌（v1 不持久） | **新增** |

> `MB_REG_HOLD_COUNT` 由 15 扩到 **64**（`0x00–0x3F`）。这是兼容性变更：读 `0x00–0x0E` 行为不变，
> 读 `0x0F` 仍异常 0x02，写 `0x0F` 仍异常 0x02；仅"读/写 ≥0x10"从异常 0x02 变为正常 —— 属功能扩展，不算破坏。
> 上限 64 使 `0x10` 单次 FC03 可读满 `0x10–0x4F`？不：`MB_FC_MAX_QTY_HOLDING=125` 远大于 64，一次可读全表。

### 3.3 输入寄存器（FC04）—— 由死契约转为活契约

v2.0 里 `s_input[4]` 恒为 0 且 **FC04 无 handler**（声明了 `0x04` 常量却返回异常 0x01）。本契约实现它：

| PDU | DW | key | 含义 | CAN | MQTT |
|---|---|---|---|---|---|
| 0x00 | 30001 | `in_adc1` | ADC1 IN | – | `…/telemetry."adc1"` |
| 0x01 | 30002 | `in_adc2` | ADC2 IN | – | – |
| 0x02 | 30003 | `in_mcu_temp` | 内核温度 0.1℃ | – | `…/telemetry."mcu_t"` |
| 0x03 | 30004 | `in_vref` | VREFINT mV | – | `…/telemetry."vref"` |

理由：`0x20–0x22` 与 `30001–30004` 内容重复是**有意的** —— 前者给 MQTT/CAN 用（连续、稳定），
后者保留 Modbus 标准语义（真实工业从站就是靠 FC04 暴露不可写瞬态量）。PC 侧验收 A-07 交叉比对两者，
不一致即为 bug。

## 4. CAN 层规格

### 4.1 位时序（沿用 v3.0，不重算）

```
CAN 内核时钟 = PCLK1 = 150 MHz
Prescaler = 30  →  tq = 30/150 MHz = 200 ns
位结构 = 1(SYNC) + Seg1(7) + Seg2(2) = 10 tq = 2 µs  →  500 kbit/s
采样点 = (1+7)/10 = 80 %      SJW = 2  (≤ min(Seg1,Seg2)+1 = 3 ✓)
```
上表在 `can.c` 的 `s_bitrateTable[]` 中：`{125k→120, 250k→60, 500k→30, 1M→15}`，Seg1=7 / Seg2=2 固定。
**本项目只用 500 k，不改这张表。** 单帧（含 8 B 数据）≈ 108 bit ≈ 216 µs。

### 4.2 帧 ID 分配

节点号 `N`：A 板(网关) `N=0`，B 板(采集节点) `N=1`。

| ID | 方向 | DLC | 触发 | 用途 |
|---|---|---|---|---|
| `0x100+N` | node → gw | 8 | 周期 1 s | **TELEMETRY_FAST**：`0x00–0x03` 四点，全 BE u16 |
| `0x110+N` | node → gw | 8 | 周期 5 s | **STATUS**：状态/链路/契约元数据（见 §4.3） |
| `0x120+N` | node → gw | 8 | 周期 10 s | **COUNTERS**：4 个 BE u16 计数 |
| `0x1A0` | gw → node | — | 周期 30 s + 按需 | **SNAPSHOT 信道（A→B 方向）**：ISO-TP 单帧为快照请求，同时承载该方向的流控 FC |
| `0x181` | node → gw | — | 周期 30 s + 按需 | **SNAPSHOT 信道（B→A 方向）**：ISO-TP 多帧，全表 0x00–0x37 |
| `0x200+N` | node → gw | 8 | 事件驱动 | **EVENT**：告警/异常/掉电恢复 |
| `0x300+N` | gw → node | 8 | 按需 | **CMD**：下行写单寄存器（FC06 语义） |
| `0x380+N` | node → gw | 8 | 事件驱动 | **CMD_ACK**：与 `cmd_id` 匹配 |
| `0x500+N` | 双向 | 4 | 周期 1 s | **HB 心跳**：3 s 无对端判链路断 |
| `0x7E0` / `0x7E8` | gw↔node | — | 按需 | **ISO-TP + UDS 诊断**（v3.0 原样保留，不改号） |
| `0x1F5` | 单板 | 8 | `CAN_DEBUG_SELFTEST` | 外环回自测帧（v3.0 原样） |

已废弃：v3.0 应用协议 `0x321`/`0x322`（A→B cmd / B→A resp 请求-应答心跳）—— 其职责被
`0x500+N` 心跳 + `0x300+N` CMD + `0x100+N` 遥测 三者分解取代。**`CAN_EncodeCmd/CAN_EncodeResp` 从契约中删除**，
不留兼容层。

### 4.3 帧内字节布局

`0x101` TELEMETRY_FAST（B 板 → A 板，1 s）

```
B0-B1 temp      u16 BE   (raw, ×0.1)
B2-B3 humi      u16 BE
B4-B5 volt      u16 BE
B6-B7 curr      u16 BE
```
无应用层头，无 CRC —— 理由：CAN 2.0 帧本身有 15-bit CRC，且 `0x101` 每帧可从对端 `0x501` 心跳的 `seq`
推断丢帧；额外 CRC 只增加延迟不增加信息。丢帧核算由 `hb_seq` 与 A 板 `can_rx` 计数比对完成（见 05 号文档 A-03）。

`0x111` STATUS（5 s）

```
B0 status(0x04) B1 errcode(0x05) B2 link_mask(0x17) B3 contract_hash(0x18) lo
B4 contract_ver(0x19) B5 form_mode(0x1A) B6 fw_ver(0x1B) lo B7 hb_seq(0x1C) lo
```

`0x121` COUNTERS（10 s，全 BE u16）

```
B0-B1 rx_cnt(0x06) B2-B3 tx_cnt(0x07) B4-B5 crc_err(0x08) B6-B7 adc1_raw(0x20)
```

`0x201` EVENT（事件驱动）

```
B0 log_event_t 枚举  B1-B3 param[3]  B4 seq  B5-B6 reserved=0  B7 0xA5 帧类型哨兵
```
枚举沿用 `Common/types.h::log_event_t`：`LOG_BOOT/LOG_RX_OK/LOG_TX_OK/LOG_TIMEOUT/LOG_CRC_ERROR/
LOG_EXCEPTION/LOG_CONFIG_CHANGE/LOG_SYSTEM_ERROR`。新增 `LOG_LINK_UP=8, LOG_LINK_DOWN=9,
LOG_MQTT_RECONNECT=10, LOG_BACKFILL=11`。

`0x301` CMD（下行，A→B，DLC8）

```
B0 fc (0x06 或 0x10)   B1 cmd_id    B2-B3 reg_addr BE   B4-B5 value BE
B6 子数量(0x10 时用)   B7 0x5C 命令哨兵
```
B 板 `can_router` 校验 B7==0x5C 与地址范围后，**直接调用 `MB_REG_SetHolding()` + 触发与 RS485 侧同一条
`Slave_ApplyConfigChange()` 路径**（写 0x09–0x0E 即置 `s_cfg_dirty`，从而复用既有的 24C02 保存 + 从站地址/波特率热切换）。
即：**CAN 下行命令不另起一套配置生效逻辑**，与 RS485 写寄存器完全等价。这是消除"两条路改配置行为不同"这一
经典工业 bug 的关键约束。

`0x381` CMD_ACK：`B0 cmd_id  B1 result(0/1/2)  B2 exccode  B3-B4 reg_addr BE  B5-B6 value_echo BE  B7 0xA5`

`0x501` HB（DLC4）：`B0-B1 uptime_s BE  B2 hb_seq(u8 环绕)  B3 node_role`

### 4.4 SNAPSHOT 载荷（ISO-TP，复用 v3.0 `isotp.c`）

信道：A→B 用 `0x1A0`（请求为 ISO-TP 单帧 `02 03 <cmd_id>`；该方向流控 FC 也走此 ID），
B→A 用 `0x181`（FF + CF×5）。与 v3.0 `isotp.c` 的"固定 rxId/txId"模型一致，无需改该模块。

```
偏移  长度  字段
0     1     ver        = 0x01
1     1     node       = 0x01
2     2     reg_count  BE = 64
4     128   regs[]     BE，自 PDU 0x00 起连续
132   2     reserved   = 0x0000
134   2     crc16      = MODBUS_CRC16(前 134 字节)，LE 在前
      合计  136 B   ≤ ISOTP_MAX_MSG 128 ❌
```
**超限，必须裁剪**。`ISOTP_MAX_MSG = 128` 是 v3.0 的编译期常量。两个选项：

- **采纳**：`reg_count` 只覆盖 `0x00–0x37`（56 个寄存器 = 112 B）→ 总 120 B ≤ 128 ✓，
  `0x38–0x3F` 为预留槽，v1 不出现在任何投影中（既不进快照，也不进 `meta` 的 `dp[]`）。
- 备选：把 `ISOTP_MAX_MSG` 提到 160，并重算 `isotp.c` 的重组缓冲（会引入新代码路径，放弃）。

冻结为 **56 寄存器 / 120 B**。总传输 = 1 FF + 5 CF + 1 FC = 7 帧，
STmin=2 ms → 空口 ≈ 7×216 µs + 5×2 ms ≈ **12 ms**；30 s 一次 → 总线负载 ≈ 0.04 %。

### 4.5 硬件过滤器（合并时需把 `StdFiltersNbr` 由 2 提到 4）

沿用 v3.0 的"默认全局过滤器 = REJECT，白名单显式放行"策略，这是抗广播风暴的正确默认。

| 板 | 元素 | SFID1 (期望 ID) | SFMR1 (掩码) | 放行范围 → 覆盖的帧 |
|---|---|---|---|---|
| A 板(网关) | 0 | `0x100` | `0x700` | `0x100–0x1FF` → `0x101` 遥测、`0x111` 状态、`0x121` 计数、`0x181` 快照数据 |
| | 1 | `0x200` | `0x600` | `0x200–0x3FF` → `0x201` EVENT、`0x381` CMD_ACK |
| | 2 | `0x500` | `0x700` | `0x500–0x5FF` → `0x501` HB |
| | 3 | `0x7E8` | `0x7FF` | `0x7E8` → UDS 应答（A 为 Tester） |
| B 板(节点) | 0 | `0x300` | `0x700` | `0x300–0x3FF` → `0x301` CMD |
| | 1 | `0x1A0` | `0x7FF` | `0x1A0` → 快照请求 + 该方向 ISO-TP 流控 |
| | 2 | `0x500` | `0x700` | `0x500–0x5FF` → `0x500` HB（A 板的） |
| | 3 | `0x7E0` | `0x7FF` | `0x7E0` → UDS 请求（B 为被诊断端点） |

掩码语义（FDCAN 经典帧过滤器）：`SFMR1` 中**置 1 的位表示"必须相等"**，故 `ID=0x100 / Mask=0x700`
只约束 bit8–bit10 → 放行 `0x100–0x1FF`；`Mask=0x600` 约束 bit9–bit10 → 放行 `0x200–0x3FF`。
B 板不需要放行 `0x381`（那是它自己发出的 ACK），也不需要整段 `0x100–0x1FF`（否则会把自身遥测段的
异常回环当输入），故快照信道用精确匹配 `0x1A0/0x7FF`。
`StdFiltersNbr` 由 v3.0 的 2 提到 **4**，两板各自的上表按 `NODE_ROLE` 编译期二选一。

### 4.6 接收路由（新增模块 `Gateway/can_router.c`）

v3.0 的 `HAL_FDCAN_RxFifo0Callback` **不解析 ID**，只把 `id/len/data` 压入 16 深度 SPSC ring，
分发发生在主循环 `App_HandleRx()` 与 `IsoTp_OnCanFrame()`（后者自过滤 `rxId`）。
新系统保留这个"ISR 只入队"的正确做法，但把主循环分发升级为**表驱动路由**：

```c
typedef struct { uint16_t id_mask, id_value; uint8_t dlc_min; void (*handler)(const can_msg_t*); } can_route_t;
extern const can_route_t g_can_routes[];   /* 由 dp_table 同源生成 */
```
新增帧类型 = 加一行表 + 一个 handler，不改分发 switch。

## 5. MQTT 层规格

### 5.1 主题表

前缀宏 `MQTT_TOPIC_PREFIX "gac/line1/gwA"`。

| 主题 | QoS | Retain | 周期 | payload |
|---|---|---|---|---|
| `{PFX}/n{n}/telemetry` | 0 | 否 | 1 s | `{"seq":123,"ts":45678,"temp":28.6,"humi":63.2,"volt":12.08,"curr":1.25,"adc1":2048,"mcu_t":41.2,"vref":1020}` |
| `{PFX}/n{n}/status` | 1 | **是** | 5 s | `{"st":1,"er":0,"lk":13,"ch":"A91F","cv":1,"ts":45678,"heap":3120}` |
| `{PFX}/n{n}/counters` | 0 | 否 | 10 s | `{"rx":1234,"tx":1230,"crc":2,"can_ack":4510,"can_ovr":0,"can_bo":1,"can_lat":3,"mb_to":3,"mb_rt":5,"mb_exc":0}` |
| `{PFX}/n{n}/snapshot` | 1 | 否 | 30 s | `{"cv":1,"ch":"A91F","regs":{"40001":286,"40002":632, … ,"40048":0}}` |
| `{PFX}/n{n}/event` | 1 | 否 | 即时 | `{"ev":9,"p":[1,0,0],"seq":88,"ts":45670}` |
| `{PFX}/n{n}/cmd` | 1 | — | 下行订阅 | `{"id":7,"fc":6,"a":9,"v":300}` |
| `{PFX}/n{n}/cmd_ack` | 1 | 否 | 即时 | `{"id":7,"ok":1,"ex":0}` |
| `{PFX}/meta` | 1 | **是** | 上电 + 变更 | `{"fw":"1.0.0","cv":1,"ch":"A91F","role":"GW","form":"M2","can":"500k","mb_baud":115200,"mb_sid":1,"dp":[["temp",0,1,"RO"],["humi",1,1,"RO"], …]}` |
| `{PFX}/n0/lwt` | 1 | 是 | broker 代发 | `{"online":false}` |

**payload 长度预算**：`meta` 最长，9 个标量 + 56 条 dp 描述 ≈ **640 B**。
→ `MQTT_SEND_BUF = 768`、`MQTT_RECV_BUF = 256`（`cmd` 最短）。固定静态数组，**禁止 malloc**。
`telemetry` ≈ 108 B，`snapshot` ≈ 56×13 + 24 ≈ **750 B** —— 超 `meta`。
故 `MQTT_SEND_BUF = 896`，且 `snapshot` 单独允许分片为 2 条消息（`regs` / `regs2`）。
RAM 代价 896+256 = 1.15 KB，可接受（见 04 号文档 §6 预算表）。

### 5.2 定点小数格式化（禁止 `%f`）

newlib-nano 的 `%f` 会拉入浮点格式化路径（数 KB flash + 不可控时延）。契约规定：

```c
/* 输出 raw/10^s，s∈{0,1,2}，纯整数运算，返回写入长度 */
int fmt_fixed(char *out, int32_t raw, uint8_t s);
/* 286,1 -> "28.6"   1208,2 -> "12.08"   0,1 -> "0.0"   -50,1 -> "-5.0" */
```
所有 `scale≠0` 的字段必须经此函数。PC 侧比对规则：**字符串精确相等**，不做浮点容差 —— 容差会掩盖刻度错误。

### 5.3 QoS / 重连 / 补发策略

| 项 | 取值 | 理由 |
|---|---|---|
| keepalive | 30 s | broker 侧 3× 未收到即判死，最坏 90 s 检出 |
| clean session | **false** | QoS1 未确认报文需 broker 持久化（mosquitto `persistence true`） |
| client id | `g474-{site}-{gw}-{node}` | 重启不变，保证 session 复用 |
| 遥测类 QoS | 0 | 1 s 周期，丢一拍由下一拍覆盖，无需重传 |
| 状态/事件/快照/命令 QoS | 1 | 必须至少到一次；用 `seq` 去重 |
| 重连退避 | **复用 `can.c` 的指数退避算法**：1 s→2→4→8→16→30 s 封顶，成功后复位 | 与 bus-off 恢复同一套已被验证的退避语义，减少一种算法 |
| 离线缓存 | `Storage/log` 新增 `LOG_MQTT_PENDING` 记录类型（32 B/条，含 `seq`） | 依据 D-07 |
| 补发顺序 | 严格 `seq` 升序，每次唤醒最多补 8 条（避免补发风暴压制实时遥测） | 可核算：断网 60 s → 补发 ≤ 8 轮 ≈ ≤ 24 s |
| 缓存溢出 | 覆盖最旧（环形天然行为），并记 `LOG_BACKFILL` 事件带被覆盖条数 | 工业场景"最新数据优先" |

**容量核算**：log 区 64 KB / 记录 32 B = **2048 条**。若事件与待发报文共用，按 1 s telemetry + 5 s status
+ 10 s counters ≈ 1.3 条/s 计入待发 → 2048 / 1.3 ≈ **1575 s ≈ 26 min 断网缓冲**。
但同一区还要存事件日志与任务超时记录，故按 50/50 静态配额：待发 1024 条 ≈ **13 min**，事件 1024 条。
分区实现细节记为 v0.6 工作项（04 号文档 §6）。

## 6. 契约哈希的可复现定义

```
输入串 = 对 dp_table[] 每一行按顺序拼接：  key ':' pdu(2hex) ':' scale ':' rw
         行间以 '\n' 分隔，末尾无换行
算法   = MODBUS_CRC16（查表版，init 0xFFFF，poly 反射 0xA001）
输出   = 4 位大写十六进制
```
- 由 `Common/dp_table.c` 在编译期展开为静态串（v1 用生成脚本，或首行运行时惰性计算一次并缓存到 `0x18`）。
- PC 侧 `Tools/python/contract_check.py` 从同一份 `dp_table.json` 算出哈希，与固件 `40025` 寄存器值比对。
  **该脚本是 v0.3 的出口条件**（05 号文档）。

## 7. 下行写闭环（MQTT cmd → CAN → B 板寄存器）

```
PC: mosquitto_pub -t gac/line1/gwA/n1/cmd -m '{"id":7,"fc":6,"a":9,"v":300}'
 ↓ A 板 mqtt_task 解析（MQTTPacket_decode + 极简 JSON 取值，仅认 id/fc/a/v 四键）
 ↓ 校验 a ∈ 可写集合 {0x09..0x0E, 0x30..0x3F}，否则就地 NRC 0x02 回 cmd_ack
 ↓ 组 0x301 帧（含 cmd_id=7）→ can_task 发送队列 → FDCAN2 → TxEventFifo 确认
 ↓ B 板 can_router 命中 CMD → MB_REG_SetHolding(0x09,300) → s_cfg_dirty
 ↓ B 板 Slave_ApplyConfigChange()（既有 20 ms 消抖路径）→ CONFIG_Save → 24C02
 ↓ B 板回 0x381 CMD_ACK{cmd_id=7, result=1}
 ↓ A 板按 cmd_id 匹配 → 发布 gac/line1/gwA/n1/cmd_ack {"id":7,"ok":1,"ex":0}
```
**超时**：A 板发出 CMD 后 500 ms 未收到同 `cmd_id` 的 ACK → 重发 1 次 → 仍失败则 `cmd_ack{"ok":0,"ex":255}`。
**幂等**：`cmd_id` 由 A 板递增（u8 环绕），B 板对同 `cmd_id` 的重复帧只执行一次（缓存最近 8 个 id）。
**匹配语义沿用 CAN 工程 v3.0 的 `0x301→0x401` ACK-by-seq 模式**，该模式已在参考项目
`MoneShadow/stm32-industrial-protocol-gateway` 中以同样理由实现（FC06 回显只代表"已接受"，不代表"已执行"）。
