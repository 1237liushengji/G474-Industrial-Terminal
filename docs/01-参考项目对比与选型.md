# 01 · GitHub 同类项目对比与选型

> ⚠ **本文件受 [07 号文档](07-板级硬件核对与冲突修正.md) 修订（2026-09-21）**：
> §5 中"板载 RS485/FDCAN/W25Q128/24C02"的表述不准确 —— 板上只有 W25Q128，
> RS485/ESP-12F/24C02 均为**外接模块**；"RS485 与 WiFi 在 AF 表层面硬互斥"也已由 07 §4 C2/C3 化解为接线问题。
> 但这些修正**不改变本文件的选型结论**：没有任何参考项目同时面对"双 G474 + 板载 Flash 与 CAN 抢引脚 +
> 外接模块化 RS485/WiFi + 设备侧 MQTT + flash 环形补发"这一组合，故自研结论维持。

> 检索日期 2026-09-21，方法：GitHub REST `/search/repositories`（按 star 排序）+ 逐仓 README 精读。
> 检索词：`modbus mqtt bridge`、`can2mqtt`、`modbus gateway stm32`、`mqtt embedded c client`、
> `freemodbus`、`cantools`、`stm32 can mqtt`、`store-and-forward mqtt embedded`（后者 0 命中）。
> **结论：没有与本方案完全同构的开源项目**（STM32G474×2 + 板载 RS485 + FDCAN + ESP-12F 透传 + 双 TFT + 板载 SPI Flash 离线缓存）。
> 但每一块都有可借的成熟实现，逐条列在下面。

## 1. 高相关：CAN ↔ Modbus 网关（与本项目硬件最接近的三个）

| 项目 | 硬件/栈 | 可借鉴点 | 与本项目差异 | 采纳 |
|---|---|---|---|---|
| **`KahanaT800/stm32-canfd-modbus-gateway`** (★1, C) | **STM32G474** + FreeRTOS + FDCAN + Modbus RTU slave + PC EMS simulator | ① 同型号 MCU，其"CAN RX / CAN TX / Modbus 处理"三任务切分与队列组织可直接对照 ② 固定 CAN ID ↔ holding register 映射表的呈现方式（显示地址 `40001` 风格 + 协议偏移双列，本方案 03 号文档沿用） ③ PC 侧 simulator + JSON Lines/CSV 双输出 + 10 个 Python 单测覆盖 CRC/frame/transport-mock/解码 ④ 用 ST-LINK VCP 当 Modbus 物理层 | 它是 **CAN-FD(500k/2M) → Modbus 从站**，STM32 不主动轮询；本任务是经典 CAN 500k + B 板做从站 + 设备侧上云。它无 MQTT、无离线缓存、无 TFT | ★★★ 借：映射表呈现法、PC simulator 分层（transport mock 化）、任务切分。**不借**：CAN-FD |
| **`MoneShadow/stm32-industrial-protocol-gateway`** (★3, C) | STM32F407 + FreeRTOS + CAN 2.0A 500k + Modbus RTU slave；F103 当模拟 CAN 设备节点 | ① **与本方案几乎同构的数据链**：`F103 状态帧 → F407 CAN RX → Device Model → Modbus 0x03 → PC`，以及反向 `PC 0x06 → 控制命令队列 → CAN 0x301 → F103 → ACK 0x401 匹配` ② 明确记录了一条关键语义：**"FC06 回显只代表 F407 已接受，不代表 F103 已执行"，真实执行结果由 CAN ACK 返回并按命令类型+序号匹配** —— 本方案 03 号文档 §7 的 `cmd_id` 幂等匹配就是这个模式 ③ 心跳 + ACK + 超时重传的三件套 ④ CAN 接收端同时校验帧类型/CAN ID/DLC，非法业务帧忽略 | 它无 WiFi/MQTT（PC 经 USB-RS485 接入）；Node ID 固定为 1；无离线缓存 | ★★★★ 借：命令-ACK 按序号匹配、Device Model 作中间层、CAN 帧合法性四重校验 |
| **`niko666-donk666/industrial-gateway`** (★3, C/C++/Qt) | STM32F103 + FreeRTOS + **ESP32-WROOM 做 WiFi/MQTT 协处理器** + RS485/Modbus RTU 主站 + Qt 上位机 + OLED | ① **双芯片分工**与本方案的 STM32+ESP-12F 同构：STM32 采集、协处理器上云 ② 主题设计 `industrial_gateway/<device-id>/{status,telemetry,modbus}` —— 本方案 `gac/{site}/{gw}/{node}/{kind}` 是它的分级扩展 ③ **网络中断时保留本地采集与就地显示，恢复后自动继续上报**（离线自治要求，本方案 §4 硬要求的同款） ④ 用"心跳/ACK/超时重传/在线状态/错误计数"做**故障定位**（对应本方案链路位图 `0x17` + 故障注入矩阵） ⑤ 它把 STM32↔ESP32 链路自定义为 UART ASCII 帧 + 心跳 + ACK | 它是 STM32→ESP32 的 **AT/自定义帧**分工，MQTT 语义在 ESP32 侧；本方案 D-04 刻意反过来（MQTT-C 在 STM32）。它无 CAN、无 SPI Flash 缓存、无 Modbus 从站侧 | ★★★ 借：主题分级、离线自治验收口径、断链自动恢复的实验设计（它有"实验记录索引"文档，值得模仿） |

## 5. 为什么必须自研而非直接选用某个开源网关

| 缺口 | 说明 |
|---|---|
| 硬件组合独特 | 双 STM32G474VET6 + **板载 16 MB W25Q128（SPI2/PB12-PB15）** + 双 TFT；RS485 与 ESP-12F 为**外接模块**，
且板载 Flash 与 FDCAN2 抢 PB12/PB13（07 §4 C1）—— 没有任何参考项目面对同一约束 |
| 无现成"设备侧 MQTT + ESP 纯 TCP 管道 + 双总线"三合一 | `niko666` 把 MQTT 放协处理器；`MoneShadow` 根本没 MQTT；`KahanaT800` 只到 Modbus 出口 |
| 已有资产的价值高于外部库 | 自研 `Protocol/` 有 256/256 CRC 表项交叉验证、11 条黄金向量、10000 帧压力门径、HAL-free 可 PC 编译测试 —— 换任何库都要重付这笔成本 |
| 真实缺口 | 上面所有项目都**不做**：QoS1 未确认报文的 flash 环形补发 + 每轮限量（防爆发）。这块是本方案 `Network/backfill.c` 的原创点，也是 v0.6 的真正难度 |

## 7. 未解问题（需要真机或后续检索确认）

1. **ESP-12F 出厂 AT 固件版本**未确认。D-04 已把要求降到最低（只需 `AT+CIPSTART` + `AT+CIPMODE=1` 透传，AT 1.7 也支持），
   但仍需上电 `AT+GMR` 实测。若 AT 完全不可用（如被刷成自定义固件），退路是刷官方 ESP-AT v2.x bin（需 USB-TTL）。
2. **板载 3.3 V LDO 能否承受 ESP-12F 发射峰值**（300–400 mA）未确认 → R-4，v0.6 前置测量。
3. `KahanaT800` 项目 star 数为 1，社区证据弱；它的价值在"同芯片 + 同协议对"的**实现细节参考**，不在成熟度背书。
4. **24C02 用的是 5 V 还是 3.3 V 模块**在所有参考项目里都不会遇到（他们没有外接 EEPROM 模块）；
   PA15(JTDI) 的 SWJ 冲突是本板独有风险，见 R-1。另新增一处本板独有的烧板风险：PB10/PB11 是 **TT 型
   （仅 3.3 V 容忍）**，接 5 V 逻辑的 RS485 模块会超压 —— 见 07 §4 C7 与 R-8。
